# Assumptions and Architectural Decisions Log

This document records key decisions, assumptions, and conflict resolutions made during the design and construction of the ORCA platform.

---

## 1. Conflict Resolutions

### 1.1 Academic Deliverables vs. Production Software
- **Context:** The course guidelines in `C:\Users\thetu\Documents\Bennett Study\SEM 1\Sustainability\Technology and Sustainability Mini Project Guidelines.pdf` require a 9-chapter academic report, presentation slides, BMC, video demonstration scripts, and LinkedIn post. The technical docs in `Files/` describe a production web service.
- **Decision:** As governed by the conflict rule ("Course requirements win on what must be delivered, and technical docs win on how it is built"), we deliver the complete working full-stack production software in `frontend/`, `backend/`, and `infra/`, AND generate the complete set of academic course deliverables in `deliverables/`.

### 1.2 Frontend Architecture (Vite SPA vs. Next.js)
- **Context:** Next.js introduces SSR and server actions that would duplicate Django's role as the single backend authority and introduce dual-server complexity.
- **Decision:** Vite + React 18+ SPA in TypeScript strict mode, deployed statically (Cloudflare Pages) with client-side routing, TanStack Query, and a custom Service Worker.

### 1.3 Risk Assessment Authority
- **Context:** Generative AI models are prone to hallucination and cannot be trusted with safety-critical decisions that affect human lives at sea.
- **Decision:** Purely deterministic rules engine (`backend/apps/risk/rules.py`). Pure Python functions with zero database, zero network, zero LLM, and zero clock reads. The LLM only handles intent routing and natural language explanation generation. All numeric assertions generated by the LLM are checked by `agents/validators.py` against the structured tool results.

## 2. Infrastructure & Local Development Assumptions

### 2.1 Domain Resolution via `localtest.me`
- **Decision:** Local development relies on `app.localtest.me:5173` and `api.localtest.me:8000`. `*.localtest.me` is a public DNS wildcard that resolves to `127.0.0.1`. This allows standard session cookies with `Domain=.localtest.me` to be shared between frontend and API without requiring manual `hosts` file modification on Windows.

### 2.2 Docker & GeoDjango Dependencies
- **Decision:** GeoDjango requires GDAL, GEOS, and PROJ libraries. While Python 3.14 is installed on the host, installing and compiling C++ GDAL bindings on Windows can be fragile. Docker Desktop with Compose (`infra/docker-compose.yml`) provides the primary containerised runtime with Debian-based GDAL binaries and PostGIS 16+. In case Docker is paused or starting, a local venv or mock fallback is supported for unit tests.

### 2.3 Cloudflare Turnstile Development Keys
- **Decision:** Testing uses Cloudflare's published dummy site keys:
  - Site Key: `1x00000000000000000000AA` (Always passes)
  - Secret Key: `1x0000000000000000000000000000000AA`
  - Site Key: `2x00000000000000000000AB` (Always blocks / fails)

### 2.4 LLM Fallback Provider
- **Decision:** `LLM_PROVIDER=template` is enabled by default so the entire application, test suite, and offline mode function without requiring paid API keys. Production supports `gemini` and `anthropic` providers configurable via environment variables.

### 2.5 Risk Thresholds as Development Placeholders
- **Decision:** The risk thresholds defined in `apps/risk/thresholds.py` are explicitly documented as development placeholders and marked with UI banners ("Demo data / Placeholder thresholds: Consult official INCOIS/IMD forecasts before venturing to sea").
